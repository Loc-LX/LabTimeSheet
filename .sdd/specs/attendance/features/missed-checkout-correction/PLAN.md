## Part MC — Missed-checkout correction

This plan delivers the correction feature and its attendance-owned contract work. Punches and their attached historical policy belong to Attendance; the responsible-Mentor relationship belongs to Internship; period finalization and reopening belong to their feature. No repository or entity crosses those module boundaries.

This plan carries the correction part of data-model `C-05`: `ck_attendance_corrections_pending_decision` counts `OVERDUE` as undecided (`DB-018`), and correction entries carry a reason for an amendment or a reversal and refuse update and delete (`DB-017`). The Leave part ships with its own plan as its own Flyway migration numbered at implementation time. The attendance-exception plan carries no attendance contract migration, because V3 already creates its tables with the `DB-016` constraints and the append-only trigger.

Tasks run on the part C integration branch `work/fix/architecture/schema-contracts`.

### Order of work

Tasks MC-01 through MC-05 are in [TASKS.md](TASKS.md). MC-01 through MC-03 use existing Intern ownership and relationship facts and can start without B-02. MC-04 contains responsible-Mentor decisions and waits for the authorization policy. MC-04 starts after part B's authorization policy (B-02) is on main and merged into the part C branch. Each behavior task starts with its smallest PostgreSQL/Testcontainers acceptance test and records the expected RED before production changes. Run GitNexus impact before each symbol change, confirm `UNKNOWN` with text search, and report HIGH/CRITICAL risk before proceeding. Test Javadoc names the rule, observable failure, and hand-derived expected value; changed public/protected members receive Javadoc in the same step.

1. **MC-01 — C-05 correction predicates and retained history.** Before migration, identify the database from Flyway history and read the correction rows, stored deadlines, lock timestamps, and correction-event kinds used by C.2/C.5; record history and counts in root `plan.md`. Stop and report to the maintainer if history has the conflicting `V2`, or if a stored shape is not described by C.5/D39. Write the PostgreSQL/Testcontainers predicate probes RED. Tighten `ck_attendance_corrections_pending_decision` so `OVERDUE` is undecided and tighten correction-event checks for reasoned amendments/reversals and forbidden new `AUTO_REJECTED`/`LOCKED` events. In the same change, update correction code to write no lock timestamp and no new lock event; keep the `locked_at` column and `ck_attendance_corrections_locked_state` for history. Preserve every existing correction deadline; use 48 hours only for new requests. Inspect both demo seed scripts and regenerate them in the same change, never hand-patch them, if any correction row/event violates the tightened predicates. Update the affected physical diagram in that change. Do not rewrite old deadlines, locks, or events. This contract task does not wait for B-02. Cover `AC-DB-006` and `AC-DB-011`.
2. **MC-02 — Submission eligibility and 48-hour windows.** Keep owning-Intern, raw-checkout, attached-policy cutoff, proposal, uniqueness, and period-open checks; use the inclusive scheduled-end-plus-48-hour submission deadline and separate submitted-at-plus-48-hour decision window. Only new rows use those windows; existing rows keep their stored deadlines. This task does not wait for B-02. Cover `AC-COR-001`, `AC-COR-002`, and `AC-COR-005`.
3. **MC-03 — Overdue state, scheduler, and notifications.** Change scheduler, request-time and history-read deadline guards to move only `PENDING` requests to `OVERDUE`, idempotently, without rejecting, locking, or recording a decision. Use `ix_attendance_corrections_pending_deadline` for the `PENDING` scan; after transition an `OVERDUE` row is not scanned again. Notify the responsible Mentor once when a request is submitted and again when it becomes overdue; notify the Intern on a decision change. Use `NOT-011`, `NotificationService.publish`, existing correction event types, and `projectId = null`. This task does not wait for B-02. Cover `AC-COR-005`, `AC-DB-006`, and `AC-ATT-009`.
4. **MC-04 — Responsible-Mentor decision history.** starts after part B's authorization policy (B-02) is on main and merged into the part C branch. Use `AUTH-012`/`ACC-026` for approve, reject, amendment, and reversal; honor period finalization and the exact reopened range. Append each change with its kind, actor, server time, resulting decision and required reason; keep proposed checkout immutable and derive the effective result from the latest decision. Notify the Intern through the existing correction decision event types. Cover `AC-COR-003`, `AC-COR-004`, `AC-COR-006`, `AC-DB-006`, and the correction permission cells in `AC-AUTH-011`.
5. **MC-05 — Close the correction part.** Close acceptance gaps after MC-01 through MC-04; ensure the correction list/detail show `OVERDUE` and retained event history, raw/effective checkout, and only policy-permitted actions. Run the affected attendance integration/web suite and part gates; record actual results in `plan.md`. Cover `AC-COR-001`–`AC-COR-006`, `AC-ATT-009`, `AC-DB-006`, `AC-DB-011`, and the correction permission cells in `AC-AUTH-011`.

### Risks

| Risk | Handling |
|---|---|
| A target database has the conflicting `V2` history | Identify Flyway history first and stop that database pending a maintainer decision under C.2. |
| Stored correction deadlines or lock/event history is treated as new policy data | Read and count before migration; retain existing values, and stop for a stored shape C.5/D39 does not describe. |
| A tighter decision predicate admits an overdue row with a decision | Probe both accepted undecided and refused decided `OVERDUE` shapes under `AC-DB-006` and `AC-DB-011` before migration. |
| The overdue scan and `ix_attendance_corrections_pending_deadline` | The index keeps serving `PENDING` rows only. The scheduler marks `PENDING` requests past their decision window `OVERDUE`; `NOT-011` notifies the Mentor once at that transition, so `OVERDUE` rows are never scanned again. |
| A demo seed row violates the correction contract | Inspect both scripts; regenerate the seed scripts in the same change if required by C.5, then apply them after Flyway and pass disposable E2E run B. |
| A Mentor-wide route survives the authorization integration | Use B-02's policy and exercise responsible/non-responsible Mentor, Admin, finalized-period, and reopened-range outcomes. |

### Not in this part

- Leave and attendance-exception state, predicates, decisions, and notifications belong to their own plans and migrations; this plan carries only the correction part of data-model `C-05`.
- This plan does not revise submission/decision deadlines already stored on correction rows or remove `locked_at`, `ck_attendance_corrections_locked_state`, `AUTO_REJECTED`, or `LOCKED` from historical records. It stops writing new lock timestamps/events and applies the 48-hour windows only to new requests.
- Decision policy is not duplicated locally. MC-04 waits for the part B policy; MC-01 through MC-03 can proceed without it.
- `D31` constrains attendance-exception amendments, not correction amendments. Correction amendment behavior follows `COR-005` and `ATT-024`.
