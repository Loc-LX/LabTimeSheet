## Part T1 — Task management

This plan implements the Task rules in this feature's SPEC and the `P5` shared contract. It owns Task behavior; it does not copy the Project lifecycle, membership, exit, calendar, notification, or work-log contracts. The schema portion of `DB-020` is already in V3. No migration is planned here. Tasks run on the part C integration branch `work/fix/architecture/schema-contracts`.

### Order of work

Tasks T1-01 through T1-06 are in [TASKS.md](TASKS.md). The demo path comes first: predictable Task creation, useful definition and assignment behavior, comments, then status history. Work that does not change an authorization decision starts first. Build/test the invariant that creation always starts at `TODO`; the deleted-Task refusal; and transition persistence plus latest-block restoration for an already-authorized assignee. Any authorization grant or denial decision is routed through `AUTH-012`, not recreated as a TaskService role check. Only T1-05 waits for part B: T1-01 to T1-04 change no authorization decision and keep the permission checks the code already makes. Where one of their tests shows a permission the §5.2 matrix refuses, the finding is reported to part B's matrix ledger and is not fixed here.

1. **T1-01 — Create at TODO.** Start with PostgreSQL/Testcontainers RED tests for both creation paths on `PLANNED` and `ACTIVE`, each non-TODO requested initial status, self-attribution and self-notification. This task does not wait for the authorization policy; it preserves existing creation authorization and changes only the creation invariant. Cover `AC-TSK-010` and `AC-TSK-019`.
2. **T1-02 — Definitions and comments.** Close the demo path for due dates, creator/Leader controls, soft deletion, retained history and comments. Keep the permission checks the code already makes; do not add a parallel role check. Cover `AC-TSK-002`, `AC-TSK-005`, `AC-TSK-006` and `AC-TSK-011`.
3. **T1-03 — Assignment and exit integration.** Prove single/batch reassignment, DONE refusal, pending-exit targets and retained creator/assignment/work history together with P4 and P6. Keep the permission checks the code already makes. Cover `AC-TSK-001`, `AC-TSK-004`, `AC-TSK-011` and `AC-TSK-015`.
4. **T1-04 — Assignee status invariants and transition ledger.** Start the state/persistence tests now: prove ACTIVE/non-deleted guards, exact graph edges, transition insertion, latest-block restoration, reason-required reopen, atomic refusal of a wrong destination and schema append-only behavior without changing an authorization decision. Keep the permission checks the code already makes. Cover `AC-TSK-003`, `AC-TSK-016`, `AC-TSK-018`, `AC-TSK-020`, `AC-TSK-021` and the Task-transition probes in `AC-DB-007`.
5. **T1-05 — TSK-023 grant half.** Starts after part B's authorization policy (B-02) is on `main` and merged into the part C branch. Use policy decisions for current Leader and owning Mentor block, exact unblock, and reopen capabilities; refuse their other transitions and every Admin transition. Part B's B-02 removes the broad owning-Mentor grant; this task adds the Leader's grant and the exact-unblock restriction for both. Cover `AC-TSK-003`, `AC-TSK-016`, `AC-TSK-018`, `AC-AUTH-004` and `AC-AUTH-005`.
6. **T1-06 — Cross-feature closeout.** Starts after T1-05. Verify Task behavior against lifecycle P1, membership/leadership P2, exit P4, calendar and notification contracts, plus the P5/P6 joint acceptance cases. This is not a claim that adjacent feature rules are implemented by this plan.

Part B's `unbuilt-operations.tsv`, on the Authorization branch and not yet on `main`, lists "Leader block, unblock or reopen of another member's Task". Whichever of part B and this plan's code reaches `main` second deletes that line and exercises its matrix cells in the same change.

### Tests

Behavioral changes start RED with the smallest PostgreSQL/Testcontainers test for the named `AC-*` scenario. Before changing each production symbol, run GitNexus impact and report callers, processes and risk; `UNKNOWN` requires text-search confirmation, and HIGH/CRITICAL must be reported before proceeding. Test Javadoc names every numbered rule it protects, the observable break and the hand-derived expected result. Add Javadoc to changed public/protected production members in the same implementation step. Run the focused test, affected project tests, then the full Maven suite; refactor without weakening assertions and rerun the affected suite.

Use real Spring services, repositories and PostgreSQL at the tested boundary. V3 schema probes remain PostgreSQL-backed. Do not add a migration: `DB-020` is present in V3. `AC-DB-007` covers the database refusal of a reasonless reopen and update/delete of an existing transition; feature acceptance must additionally prove successful application writes and correct transition data.

### Risks

| Risk | Handling |
|---|---|
| B-02 and T1-04 both edit `TaskService#changeStatus` | Whichever of part B and part C reaches `main` second resolves the conflict, keeping B-02's refusal of the owning Mentor's other transitions and T1-04's transition record and latest-block restoration; the merge runs both parts' tests before it is committed. |
| Existing Mentor behavior exceeds the approved status grant | Replace the current service-local rule with `AUTH-012` policy decisions only after B-02 is integrated; prove both allowed and denied matrix cells. |
| Transition history is absent from application writes although V3 protects the table | Add the row in the same transaction as the Task status mutation; test rollback and unchanged history on every refusal. |
| Unblock uses a caller-selected target or an older block | Read the latest block record as the source of truth and test repeated block/unblock sequences for both `TODO` and `IN_PROGRESS`. |
| Adjacent lifecycle/exit/calendar behavior is duplicated or silently changed | Keep their contracts in the owning feature; use joint acceptance scenarios and report any SPEC/code disagreement for maintainer decision. |
| A migration appears necessary despite the V3 table | Stop and report; this plan authorizes no migration and does not modify applied V3. |
